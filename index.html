03 / SENSOR SCHEMA

实例建模 · 一条设备遥测记录

先把物理量、单位和缺失规则写进 schema

本例把电压、电流、温度、湿度和 GPS 组织成一条 Telemetry 消息。所有数字都是明确标注的演示输入；nanopb 行为则沿用本仓库 generator/runtime 的实现。

TELEMETRY.PROTO · 教学样例proto2 / stable field numbers
// 缺失的采样用 optional 表示；设备身份必须存在
syntax = "proto2";

message GpsFix {
  required sint32 latitude_e6 = 1;
  required sint32 longitude_e6 = 2;
}

message Telemetry {
  required uint32 device_id = 1;
  optional uint32 voltage_mv = 2;
  optional uint32 current_ma = 3;
  optional sint32 temperature_centi_c = 4;
  optional uint32 humidity_centi_pct = 5;
  optional GpsFix gps = 6;
}
field number 一经发布就应稳定；数字编码的选择同时影响兼容性和 wire bytes。

MISSING SAMPLE / PROTO2 OPTIONAL

缺测字段保留“未提供”状态

例如温度采样失败时，应用保持 has_temperature_centi_c = false。消息对象里该成员仍存在；编码器跳过整条字段，接收端看到的 has 标志也保持 false。

REQUIRED IDENTITY

设备标识仍然必须到达

device_id 是 required。解码消息缺少它会在 required 检查时失败。对可缺测的传感器使用 optional，避免把正常缺测变成整条消息失败。

输入齐全

所有 has_* 均为 true；每项都进入字段遍历并生成 wire bytes。

部分缺测

缺失项的 has 标志为 false；其余有效字段照常写出，消息仍能解码。

GPS 缺失

has_gps=false 时整个嵌套 GpsFix 字段省略；纬度和经度不会占文件字节。

optional / repeated / oneof / map 是字段形状，不是值类型

同一个 int32 可以是 singular、repeated 或 oneof 成员；值类型决定单个值的 wire 编码，字段形状决定出现次数、presence 和外层组织方式。

字段形状语义与 wire 影响Nanopb / 使用注意
singular / optional最多一个值。proto2 singular 有显式 presence；proto3 基础类型默认不区分“未设置”和“设为默认值”，加 optional 才有显式 presence。message 类型自身有 presence。proto2 optional 通常生成 has_*；proto3 implicit scalar 默认值可能不编码。不要把零值当成“传感器有效”的证据。
required（proto2）解码结束时必须见到该字段；缺少它会令消息解析失败。proto3 不接受 required。Nanopb 在消息结束时执行 required 检查；它不等同于 optional 的 has_* 存储形状。官方不建议把 required 用在需要长期演进的协议里。
repeated零个或多个有序值。数值、bool、enum 等 packable 类型可以用一个 LEN 段打包；string、bytes、message 按元素分别编码。静态 C 数组需 max_count；字段本身不追踪“缺失还是空数组”。packed 与 unpacked 都应被 decoder 接受。
oneof一组选项至多有一个当前值；每个成员仍使用它自己的 wire type。Nanopb 用选择标记和共享 union 存储；同组成员不能是 repeated 或 map。
map<K,V>语法糖，不是独立 scalar wire type；线上等价于 repeated entry message，entry 内 key 用 tag 1、value 用 tag 2。key 可用 bool、允许的整数类型或 string；不能用 float/double、bytes、enum 或 message。Nanopb 生成 entry 数组和 count，仓库有 tests/map/map.proto 示例。
schema 演进是 protobuf 的核心工程约束：wire 上没有字段名，字段号才是身份。常见的兼容做法是用新编号增加 optional/repeated 字段；删除字段时保留旧编号（必要时也保留旧名字）；不要重新编号或复用旧编号，因为旧数据仍可能存在。随意改变类型也可能让同一段 bytes 被新旧程序解释成不同的值。proto2 required 会让缺字段的消息解码失败，官方不建议用于需要长期演进的 schema。下面单独解释字段号为什么影响字节长度，以及哪些编号不能由应用使用。
FIELD NUMBER / ENCODED KEY

为什么 tag 1–15 的 key 通常是 1 byte？

protobuf 先把字段号和 wire type 合成 key：key = (tag << 3) | wire_type。key 再用 varint 编码；一个 varint 字节有 7 位存数值，最高位表示“后面还有没有字节”。因此 1 个字节能表示 0–127。

tag 1, wire type 0
key = (1 << 3) | 0 = 8 = 0x08
→ 1 byte

tag 15, wire type 5
key = (15 << 3) | 5 = 125 = 0x7D
→ 在 0–127 内，varint 只用 1 byte

tag 16, wire type 0
key = (16 << 3) | 0 = 128
→ 超过 127，varint 编成 80 01（2 bytes）

对比 tag 16–2047 的 2-byte key，常用字段号 1–15 每次出现少占 1 个 key 字节；字段值另行编码，可能还会占多个字节。重复字段会重复付 key 的开销。官方编码说明

RESERVED / IMPLEMENTATION SPACE

为什么 19,000–19,999 不能给应用字段用？

这段编号由 Protobuf 实现保留。应用 schema 不能声明其中的字段号，以免与库实现保留的编号空间冲突。这个范围在数学上可以编码；禁止使用是编号分配规则，不是 varint 编码限制。

  08 / WHY THE WIRE IS COMPACT
  
逐字节分析 · 规则来源于 encoder
紧凑来自字段编码规则，不是压缩黑盒
Nanopb 是面向嵌入式的 protobuf C 实现与 generator。wire 字节按字段规则编码：短 key、按数值长度变化的 varint、可省略的 optional 字段，以及可打包的 repeated 标量。内存分配策略另行控制 RAM；两种“紧凑”要分开理解。

  

    
MECHANISM 01 / FIELD KEY
字段号与 wire type 合并成 key
key = (field_number << 3) | wire_type。Telemetry 的电压字段 tag=2、wire type=0，key 为 0x10，varint 占 1 byte。小字段号让常见 key 保持短小。

    
MECHANISM 02 / VARINT
小整数只写需要的字节
每个 varint byte 携带 7 个数值位；最高位提示是否还有后续 byte。电压 3300 mV 的值部分为 E4 19 两字节，远小于把该数值固定写成 4 bytes。

    
MECHANISM 03 / PRESENCE
缺失的 optional 字段不出现在 wire 中
温度缺测时没有 tag、没有 value；字段被整体省略。消息里的其他字段仍独立编码。C 结构体仍保留成员和 has 标志，因此 RAM 占用与文件字节数要分开计算。

    
MECHANISM 04 / PACKED ARRAY
repeated 标量可以共享一次 key
默认 packed 路径写一次 length-delimited key、payload 长度和连续值；定义 PB_ENCODE_ARRAYS_UNPACKED 后每个值各自带 key。本页 wire lab 可切换查看两种布局。

    
MECHANISM 05 / RAM POLICY
变长字段可选择静态、pointer 或 callback
generator 按 max_size/max_count 或显式 type 生成结构。静态成员给出可计算上界；callback 可让应用逐段提供字段数据；pointer 需要动态内存支持。它们改变 RAM 使用方式，不改变 protobuf wire 规则。

  13 / PRACTICAL USE
  
    回到工程实践
    典型用法：生成一次，按实际长度编码与解码
    仓库 examples/simple 是最适合照着读的完整入门路径。它展示消息初始化、赋值、输出 buffer、编码、错误检查、记录实际长度，再从相同字节区解码。
    
  
    
    
    01
    写 .proto
    先稳定字段号和类型。proto2 的 required/optional/repeated 规则影响生成结构与运行时检查。
    仓库示例：SimpleMessage 有一个 required int32 字段。
    
    
    02
    限制变长字段
    按目标 RAM 预算配置 string 的 max_length/max_size、repeated 的 max_count、bytes 的 max_size。
    这些决定数组容量；不代表结构体总字节数，也不代表每条 wire 消息的长度。
    
    
    03
    生成并编译 C 文件
    编译 simple.pb.c 以及 pb_encode.c、pb_decode.c、pb_common.c。
    这是 examples/simple/Makefile 实际列出的源码集合。
    
    
    04
    初始化消息并填值
    SimpleMessage message = SimpleMessage_init_zero;，再设置 message.lucky_number = 13;。
    示例建议初始化结构体，避免未初始化 RAM 内容影响编码。
    
    
    05
    编码并检查返回值
    用 pb_ostream_from_buffer() 建输出 stream；调用 pb_encode() 并处理失败。
    buffer 满、callback I/O 失败、缺 required 字段等都会令操作失败。
    
    
    06
    保存 bytes_written
    编码完成后，stream.bytes_written 才是此条消息的准确长度。
    不要发送 sizeof(message)，也不要把 buffer 未使用的尾部发出去。
    
    
    07
    按实际长度解码
    用 pb_istream_from_buffer(buffer, message_length)，再调用 pb_decode()。
    输入边界应对应实际收到的这一条消息。

    重点实例 · 自定义字段 callback
    
    
    把连续传感器读数逐个写出，解码时逐个交给应用
    
    
    场景：设备连续采集电压，样本数量由应用数据源决定，不必在 Nanopb 消息结构里放一个预设容量的大数组。callback 让应用逐项提供数据；解码时每个值到达就交给应用处理或存入自己的缓冲。单条消息仍受 wire stream 容量、协议长度和设备资源约束。下面从 schema、生成成员、函数绑定、wire bytes 到输入 callback 的数据逐步展开。
    

    
    
      
    字段 callback · 本节主角处理某个 protobuf 字段的值。默认配置下，FT_CALLBACK 生成 pb_callback_t 成员，由应用设置 funcs.encode/decode 与 arg。
    
      
    消息级 callback · 进阶写法用 callback_datatype 让生成字段保存应用类型；生成器为整条消息绑定一个函数，函数按当前字段决定如何读写。仓库网络文件列表示例采用此形式。
    
      
    Stream I/O callback · 传输层给 pb_ostream_t/pb_istream_t 提供实际写入或读取字节的函数，例如 socket、文件或设备。它负责搬运 wire bytes，不负责字段值语义。

    手算一个样本：3300 mV → 08 E4 19
    
      
    字段号 1、wire type 0：key = (1 << 3) | 0 = 8，所以 key 是 08。3300 = 25 × 128 + 100：低 7 位组是 100（0x64），后面还有一组，所以置最高位续传标记 0x80，第一个 varint 字节变成 E4；剩余值 25（0x19）是最后一组，不置续传位。于是一个 repeated 项是 08 E4 19；三个演示值完整串为 08 E4 19 08 E5 19 08 E2 19，共 9 bytes，没有 C 结构体布局或额外的 repeated 数组长度前缀。
    
    
    

    
    
      
    ENCODE CALLBACK · 逐项输出pb_callback_t.funcs.encode
    #include <stddef.h>
#include <stdint.h>
#include <pb_encode.h>
#include "sample_batch.pb.h"

typedef struct {
    const uint32_t *values;
    size_t count;
} reading_source_t;

static bool encode_readings(pb_ostream_t *stream,
                            const pb_field_t *field,
                            void * const *arg)
{
    const reading_source_t *src = *arg;
    for (size_t i = 0; i < src->count; i++) {
        if (!pb_encode_tag_for_field(stream, field) ||
            !pb_encode_varint(stream, src->values[i]))
            return false;
    }
    return true;
}

static bool encode_demo(pb_byte_t *buf, size_t buf_size, size_t *out_len)
{
    uint32_t readings[] = {3300, 3301, 3298};
    reading_source_t src = {readings, 3};
    SampleBatch msg = SampleBatch_init_zero;
    msg.millivolts.funcs.encode = encode_readings;
    msg.millivolts.arg = &src;

    pb_ostream_t out = pb_ostream_from_buffer(buf, buf_size);
    if (!pb_encode(&out, SampleBatch_fields, &msg)) {
        /* inspect PB_GET_ERROR(&out) */
        return false;
    }
    *out_len = out.bytes_written;
    return true;
}
    encode callback 必须自己写完整字段，包括 tag/wire type；重复字段需要每个值各写一次 key。此例从可重放的本地数组读取。
    
      
    DECODE CALLBACK · 每项交给应用pb_callback_t.funcs.decode
    #include <stddef.h>
#include <stdint.h>
#include <pb_decode.h>
#include "sample_batch.pb.h"

typedef struct {
    uint32_t *values;
    size_t capacity;
    size_t count;
} reading_sink_t;

static bool decode_reading(pb_istream_t *stream,
                           const pb_field_t *field,
                           void **arg)
{
    reading_sink_t *sink = *arg;
    uint64_t value;
    (void)field;

    if (!pb_decode_varint(stream, &value) ||
        value > UINT32_MAX || sink->count >= sink->capacity)
        return false;

    sink->values[sink->count++] = (uint32_t)value;
    return true;
}

static bool decode_demo(const pb_byte_t *buf, size_t message_length)
{
    SampleBatch decoded = SampleBatch_init_zero;
    uint32_t received[8];
    reading_sink_t sink = {received, 8, 0};
    decoded.millivolts.funcs.decode = decode_reading;
    decoded.millivolts.arg = &sink; /* before pb_decode */

    pb_istream_t in = pb_istream_from_buffer(buf, message_length);
    if (!pb_decode(&in, SampleBatch_fields, &decoded)) {
        /* inspect PB_GET_ERROR(&in) */
        return false;
    }

    /* Consume received[0..sink.count) here. */
    return true;
}
    decode callback 的 stream 已经被限制到当前字段值；tag 已由 Nanopb 读取。这里的 sink 有容量上限，超出就明确返回失败。pb_callback_t.funcs 是 union；发送端绑定 encode，接收端在 pb_decode 前绑定 decode。未绑定 decode 函数时，应用不会收到该字段值。

#include <string.h>
#include <stdio.h>
#include <pb_encode.h>
#include <pb_decode.h>

/* server.c：callback 拿到 ostream */
bool ListFilesResponse_callback(
    pb_istream_t *istream, pb_ostream_t *ostream,
    const pb_field_iter_t *field)
{
    PB_UNUSED(istream);
    if (ostream != NULL &&
        field->tag == ListFilesResponse_file_tag) {
        DIR *dir = *(DIR**)field->pData;
        struct dirent *file;
        FileInfo item = {};
        while ((file = readdir(dir)) != NULL) {
            item.inode = file->d_ino;
            strncpy(item.name, file->d_name, sizeof(item.name));
            item.name[sizeof(item.name) - 1] = '\0';
            if (!pb_encode_tag_for_field(ostream, field) ||
                !pb_encode_submessage(ostream,
                                      FileInfo_fields, &item))
                return false;
        }
        rewinddir(dir); /* delimited sizing pass */
    }
    return true;
}

/* client.c：独立程序中的 callback 拿到 istream */
bool ListFilesResponse_callback(
    pb_istream_t *istream, pb_ostream_t *ostream,
    const pb_field_iter_t *field)
{
    PB_UNUSED(ostream);
    if (istream != NULL &&
        field->tag == ListFilesResponse_file_tag) {
        FileInfo item = {};
        if (!pb_decode(istream, FileInfo_fields, &item))
            return false;
        printf("%s\n", item.name); /* 立即消费 */
    }
    return true;
}
    
      
    
      
    这里展示的是进阶的 callback_datatype / 消息级 callback：生成成员是 DIR*，并由生成器绑定 ListFilesResponse_callback()，不是上方的 pb_callback_t 成员。服务端先执行 response.file = directory，再调用 pb_encode_delimited()；运行库把当前字段传给 handler，server 版本从 field->pData 取回目录指针并逐项编码。上面 server 与 client 的同名函数是分别编译进两个程序的两个实现。源码注释指出 delimited 编码会调用该 callback 两次，因此每次遍历后用 rewinddir() 重置目录，确保测长和正式写出得到一致结果。对上方传感器样例也一样：callback 若从会被消费的 FIFO 取数，就必须能在重复调用时重放同一批数据。该 POSIX 示例只说明 Nanopb API 用法；嵌入式项目应换成自己的目录、文件或传感器数据源。
